# 일본어 가사에 한국어 발음·번역 붙이기 — 설계

작성 2026-09-06. 상태: **계획 확정. 코드 없음.**
방침은 §8 에서 정해졌다 — 일본어만, 요청할 때만, 항상 표시, 판별은 유니코드 범위로.

목표 두 가지다.

1. 일본어 가사 각 줄 아래에 **한글 음차(발음)** 와 **한국어 번역** 을 AI 로 채운다.
2. 그런 가사·곡 메타 설정을 **PC 앱에서 직접 고치고 다시 요청** 할 수 있게 한다.

---

## 1. 먼저 — 절반은 이미 만들어져 있다

이 기능을 위한 저장·표시 경로가 이미 존재한다. **새로 만들 것은 "AI 로 채우는 부분" 뿐이다.**

| 조각 | 상태 | 위치 |
|---|---|---|
| 줄별 발음·번역 저장 | **있음** — `lyrics.layers` (JSON 배열) | `Data/DatabaseInitializer.cs:143` |
| 저장 형식 | **있음** — `{ text, pronunciation, translation }` | `wwwroot/static/app.js` `attachLayers()` |
| 원문 아래 표시 | **있음** — `np-pron` / `np-trans` 두 줄 | `app.js` `appendSubLayers()` |
| API 노출 | **있음** — `/api/lyrics/{vid}` 응답의 `layers` | `Controllers/LyricsController.cs:63` |
| 수동 입력·저장 | **있음** — `POST /api/admin/lyrics/{vid}/manual` 의 `Layers` | `Controllers/AdminController.cs:521` |
| **AI 로 자동 생성** | **없음 ← 이번에 만들 것** | — |
| 일괄 처리·진행률 | 없음(가사 배치 구조를 그대로 본뜨면 된다) | `Services/LyricsBatchService.cs` |

즉 스키마 변경도, 화면 작업도 필요 없다. AI 가 채운 값을 기존 `layers` 에 넣기만 하면
지금 있는 UI 가 그대로 그린다.

## 2. 만들 것

### 2.1 `AiLyricsLayers` 서비스

`Services/Ai/` 에 세 번째 AI 작업으로 추가한다(기존: A 제목 파싱 / B 가사 검증 → **C 발음·번역**).

입력은 가사 줄 배열, 출력은 줄마다 `{ pronunciation, translation }`.

```
입력:  ["きみの こえが きこえる", ...]
출력:  [{ pron: "키미노 코에가 키코에루", trans: "네 목소리가 들려" }, ...]
```

기존 `AiClient` 를 그대로 쓴다 — 일일 상한·회로 차단·캐시가 이미 붙어 있다.

### 2.2 반드시 청크로 쪼개야 한다

`AiClient.MaxOutputTokens` 가 **2048** 이다(`Services/Ai/AiClient.cs:40`). 한 곡 40줄에
발음+번역을 한 번에 받으면 넘친다 — 넘치면 본문이 잘린 채 오고 JSON 파싱이 깨진다.

- **15줄씩 끊어 여러 번 호출**한다. 40줄이면 3회.
- 또는 이 작업에 한해 `maxOutputTokens` 를 호출 인자로 받게 고친다(지금은 상수).
- 곡당 3회 × `AI_DAILY_CAP` 1000 → **하루 약 330곡**. 보관함 규모면 충분하다.

### 2.3 캐시 키

`AiCache` 를 그대로 쓰되 키 입력은 **가사 본문의 해시**여야 한다. `videoId` 로 잡으면
가사가 교체됐을 때 옛 발음이 남는다.

```
AiCache.Key("lyricslayer", version, sha256(가사원문), 청크번호)
```

### 2.4 대상 판별 — 유니코드 범위로만, AI 에 묻지 않는다

일본어인지 아닌지는 **글자 코드값만 보면 확실히 알 수 있다.** 이걸 AI 에 물으면 돈과 시간이
들고 답이 흔들리기까지 한다. 순수 함수로 판별한다.

> 참고: 아스키(0~127)에는 일본어가 없다. 아스키는 영문·숫자·기호뿐이라 한글도 일본어도
> 담기지 않는다. 판별에 쓸 것은 **유니코드 범위**다.

| 대상 | 범위 | 비고 |
|---|---|---|
| 히라가나 | `U+3040`–`U+309F` | **이게 결정적 증거다** |
| 가타카나 | `U+30A0`–`U+30FF` | 〃 |
| 반각 가타카나 | `U+FF66`–`U+FF9D` | 드물지만 있다 |
| 한자(CJK 통합) | `U+4E00`–`U+9FFF` | 중국어와 겹친다 — **단독 근거로 쓰지 않는다** |
| 한글 음절 | `U+AC00`–`U+D7A3` | 이게 많으면 한국어 가사다 |

판정 규칙:

```
가나 = 히라가나 + 가타카나 + 반각가타카나 글자 수
가나가 3자 미만이면            → 대상 아님
가나 / (가나 + 한자 + 한글 + 라틴문자) < 0.05 이면 → 대상 아님 (한두 글자 섞인 것뿐)
그 외                          → 일본어 가사로 본다
```

한자만 있고 가나가 없으면 중국어일 수 있으므로 **대상에서 뺀다**. 놓치는 곡이 조금 생기지만,
엉뚱한 곡에 일본어 발음을 붙이는 것보다 낫다.

**지금은 일본어만 한다.** 영어·중국어 가사는 대상이 아니다(§8-2). 나중에 넓히더라도 이 판별
함수에 범위를 더하는 것으로 끝난다.

### 2.5 줄 매칭 주의점

`attachLayers()` 는 **줄 텍스트를 정규화한 값으로 큐 매칭**한다. 후렴처럼 같은 줄이 여러 번
나오면 순서대로 하나씩 꺼내 쓴다. 따라서 AI 에 보낼 때도 **중복 줄을 합치지 말고 원래 순서
그대로** 보내야 짝이 맞는다.

### 2.6 트리거 — 요청할 때만

**가사를 새로 찾을 때 자동으로 만들지 않는다**(§8-3). 사람이 버튼을 눌렀을 때만 만든다.
곡마다 AI 호출이 저절로 발생하는 것을 막고, 실제로 볼 곡에만 돈을 쓴다.

| 방식 | 용도 |
|---|---|
| `POST /api/lyrics/{vid}/layers` | 지금 듣는 곡 하나. 앱·웹에서 버튼 하나로 |
| 관리자 일괄 | **나중에**. 단건이 충분히 검증된 뒤에만 만든다 |

이미 만들어 둔 곡은 다시 만들지 않는다(`layers` 가 있으면 그대로 둔다). 다시 만들려면
`force` 를 명시해야 한다 — 버튼을 두 번 눌러 돈이 새는 일이 없어야 한다.

`locked = 1` 인 가사는 사람이 손본 것이므로 **건드리지 않는다**(덮어쓰기 금지).

### 2.7 표시 — 항상 보여 준다

토글을 만들지 않는다(§8-4). `layers` 가 있으면 원문 아래에 발음·번역이 늘 붙는다.
**지금 UI 가 이미 그렇게 동작하므로 이 항목은 추가 작업이 없다** — `attachLayers()` 는
조건 없이 붙이고 `appendSubLayers()` 가 값이 있는 것만 그린다.

## 2.5b 정확도를 어떻게 올릴 것인가

이 기능은 "대충 맞는 발음"이면 쓸모가 없다. 따라 부르다 틀리면 안 보느니만 못하다.
아래 다섯 가지를 **처음부터** 넣는다.

### (1) 발음과 번역을 나눠서 요청한다

한 번에 시키면 모델이 둘 다 대충 한다. 요청을 나누면 각각의 품질이 확실히 오른다.
**대신 호출이 2배**가 된다(곡당 3회 → 6회). 요청할 때만 만드는 방식(§2.6)이라
전체 비용은 감당 가능하다.

### (2) 모델을 이 작업에만 따로 지정할 수 있게 한다

지금 기본값은 `gemini-3.5-flash-lite`(`AppOptions.AiModel`)다. 제목 파싱처럼 짧은 판단에는
충분하지만 음차·번역은 더 무거운 작업이다. `AiLyricsModel` 옵션을 따로 두어 이 작업만
상위 모델로 돌릴 수 있게 한다. 비워 두면 기존 모델을 쓴다.

### (3) 프롬프트에 예시를 넣는다(few-shot)

규칙을 말로만 설명하면 지켜지지 않는다. 실제 입출력 예시를 서너 줄 박아 둔다 — 특히
조사와 촉음처럼 **표기와 소리가 다른** 경우를 예시로 보여 준다(§3).

### (4) 출력을 기계적으로 검증한다

모델을 믿지 않고 받은 값을 검사한다. 하나라도 걸리면 그 청크를 **버린다**(캐시도 하지 않는다).

| 검사 | 이유 |
|---|---|
| 줄 수가 입력과 같은가 | 어긋나면 이후 줄이 전부 밀린다 |
| 발음에 한글·공백 외의 글자가 있는가 | 일본어나 로마자가 남아 있으면 실패한 것이다 |
| 번역에 가나가 남아 있는가 | 번역이 안 된 줄이다 |
| 빈 줄·`♪` 에 값을 붙였는가 | 간주에 가사를 지어낸 것이다 |

### (5) 청크 경계에 문맥을 겹쳐 보낸다

15줄씩 자르면 경계에서 문맥이 끊겨 번역이 어색해진다. 앞뒤로 2줄씩 겹쳐 보내고
**결과는 가운데 15줄만 쓴다**. 발음은 문맥과 무관하므로 겹치지 않아도 된다.

> 그래도 틀리는 줄은 남는다. 사람이 고칠 수 있는 경로가 이미 있고(관리자 수동 저장),
> 고친 가사는 `locked` 로 보호되어 다시 덮이지 않는다.

## 3. 프롬프트에서 정해야 할 것

발음은 **로마자가 아니라 한글 음차**여야 한다("요루니 카케루", `yoru ni kakeru` 아님).
아래를 프롬프트에 못 박아야 실제로 쓸 만한 값이 나온다.

- 조사 `は`→`와`, `へ`→`에`, `を`→`오` 처럼 **표기가 아니라 소리**를 적는다.
- 촉음 `っ` 은 받침으로 적는다 — `きって` → `킷테`.
- 장음 `ー` 는 §8 에서 정한 방식으로 일관되게 적는다.
- 노래는 실제 발음이 가사 표기와 다른 경우가 있다(한자에 다른 후리가나를 붙이는 연출).
  모르면 표기대로 읽는다.
- 번역은 **직역이 아니라 자연스러운 한국어 한 줄**. 줄 수를 원문과 반드시 1:1 로 맞춘다.
- 빈 줄·간주 표시(`♪`)는 그대로 두고 발음·번역을 만들지 않는다.
- 한글과 공백 외의 글자를 발음에 쓰지 않는다(로마자·일본어 금지). 이건 §2.5b-4 에서
  기계적으로도 검사하지만, 프롬프트에도 적어 두어야 애초에 덜 틀린다.

발음 요청과 번역 요청은 **서로 다른 프롬프트로 나눠 보낸다**(§2.5b-1). 한 프롬프트에
둘을 섞으면 모델이 양쪽 다 대충 한다.

## 4. PC 앱에서 고치고 다시 요청하기

지금 앱은 **웹 화면을 띄우는 껍데기**라, `/admin` 으로 이동하면 관리자 화면이 이미 그대로
열린다. 그러니 "앱에서 설정한다"는 두 단계로 나눠 생각하는 게 좋다.

### 4.1 1단계 — 지금 듣는 곡에 대한 즉시 조작 (권장)

앱 창 오른쪽 패널(지금 디스코드 상태를 보여 주는 자리)에 버튼 몇 개를 둔다.

- `가사 다시 찾기` · `발음·번역 만들기` · `곡 메타 다시 조회`
- 각각 기존 API 를 부르면 된다. **서버 작업은 §2.6 의 엔드포인트 하나면 끝난다.**

이때 브릿지를 **양방향**으로 넓혀야 한다. 지금 `bridge.js` 는 페이지 → 앱 한 방향이다
(재생 상태 보고). 앱이 videoId 를 알아야 하므로 다음 중 하나가 필요하다.

- 브릿지가 보고에 `videoId` 를 포함시킨다(가장 간단, 한 줄 추가).
- 앱이 `CoreWebView2.PostWebMessageAsJson()` 으로 페이지에 명령을 보낸다.

> `bridge.js` 는 지금 `title`·`artist`·`pos`·`dur`·`art`·`song`·`singer` 를 보낸다.
> `videoId` 만 얹으면 앱이 API 를 직접 부를 수 있다.

### 4.2 2단계 — 설정 화면 자체

가사 소스 우선순위, AI 켜기/끄기, 일일 상한 같은 **서버 설정**은 이미 `/admin` 에 있다.
앱에 같은 UI 를 다시 만들 이유는 없다. 트레이 메뉴나 버튼에서 `/admin` 을 여는 것으로 충분하다.

**앱 자체 설정**(디스코드 표시, 확대 비율 등)은 이미 앱 설정 창에 있다. 둘을 섞지 않는 게 좋다 —
서버 설정은 라파에 저장되고 모든 기기에 영향을 주지만, 앱 설정은 이 PC 에만 적용된다.

## 5. 구현 순서

1. **일본어 판별 함수** (§2.4) — 순수 함수라 AI 없이 단독으로 검증한다. 여기부터 시작하면
   나머지 단계에서 엉뚱한 곡에 돈을 쓰는 일이 없다
2. `AiLyricsLayers` 서비스 + 프롬프트 (§2.1, §3) + 출력 검증 (§2.5b-4)
3. 청크 분할 + 문맥 겹침 + 캐시 (§2.2, §2.3, §2.5b-5)
4. `POST /api/lyrics/{vid}/layers` 단건 엔드포인트 (§2.6)
5. 웹 가사 패널에 버튼 하나 — 여기까지면 **사람이 쓸 수 있는 상태**가 된다
6. `bridge.js` 에 `videoId` 추가 + 앱 패널 버튼 (§4.1)
7. 관리자 일괄 처리 — **나중에.** 단건으로 여러 곡을 눌러 보고 품질이 납득되면 그때 만든다

5번까지가 최소 기능이다. 6·7번은 없어도 동작한다.

---

## 6. 비용

발음과 번역을 나눠 부르므로(§2.5b-1) **곡당 6회**다 — 40줄 기준 15줄씩 3청크 × 2.
요청할 때만 만들므로(§2.6) 저절로 쌓이지는 않는다. `AI_DAILY_CAP` 1000 이면 **하루 약 160곡**.

캐시가 가사 해시 기준이라(§2.3) 같은 곡을 다시 눌러도 0원이다.

곡당 6회가 부담되면 두 가지 손잡이가 있다 — 청크를 20줄로 키우거나(출력 토큰 한계에 유의),
발음·번역을 한 번에 받도록 되돌린다(품질과 맞바꾼다).

## 7. 위험 요소

| 위험 | 대응 |
|---|---|
| 발음이 어색하거나 틀림 | 사람이 고칠 수 있다 — 관리자 수동 저장이 이미 있고 `locked` 로 보호된다 |
| 줄 수가 어긋남 | 응답 줄 수가 입력과 다르면 그 청크를 통째로 버린다 |
| 출력 토큰 초과로 잘림 | §2.2 청크 분할. JSON 파싱 실패 시 캐시하지 않고 버린다 |
| 가사 교체 후 옛 발음 잔류 | 캐시 키를 가사 해시로 잡는다(§2.3) |
| 일본어 아닌 곡에 낭비 | 가나 비율로 대상 판별(§2.4). AI 를 부르기 **전에** 거른다 |
| 발음에 로마자·일본어가 남음 | 한글·공백만 허용하는 검사로 청크를 버린다(§2.5b-4) |
| 간주(`♪`)에 가사를 지어냄 | 빈 줄에 값이 붙었으면 청크를 버린다(§2.5b-4) |
| 실수로 두 번 눌러 중복 과금 | `layers` 가 이미 있으면 만들지 않는다. 다시 만들려면 `force` 명시(§2.6) |

## 8. 정해진 방침

| # | 항목 | 결정 |
|---|---|---|
| 1 | 대상 판별 | **유니코드 범위로만.** AI 에 묻지 않는다 (§2.4) |
| 2 | 대상 언어 | **일본어만.** 영어·중국어는 하지 않는다 |
| 3 | 실행 시점 | **요청할 때만.** 가사를 찾을 때 자동으로 만들지 않는다 (§2.6) |
| 4 | 표시 | **항상 보여 준다.** 토글을 만들지 않는다 (§2.7) |
| 5 | 품질 | 정확도를 우선한다 — 발음·번역 분리 호출, 출력 검증, 문맥 겹침 (§2.5b) |

### 아직 안 정한 것 하나 — 장음 표기

`ー` 를 늘려 쓸지(`토오쿄오`) 한 번만 쓸지(`토쿄`)는 취향이라 정해 주면 프롬프트에 한 줄
박는다. **권장은 늘려 쓰지 않는 쪽**이다 — 한국어 표기 관례에 맞고 읽기도 편하다.
다만 따라 부를 때 박자를 놓치지 않으려면 늘려 쓰는 게 나을 수도 있어서, 실제 결과를 몇 곡
보고 정해도 늦지 않다. 프롬프트 한 줄이라 나중에 바꾸는 비용이 거의 없다.

촉음 `っ` 은 받침으로 적는다(`きって` → `킷테`) — 이건 이견이 없어 그대로 간다.

## 9. 나무위키를 1순위 소스로 (2026-09-07 결정)

§2 는 발음·번역을 **AI 가 짓는다**고 전제했다. 그런데 사람이 이미 만들어 둔 것이 나무위키에
있다. 지어낸 것보다 사람이 쓴 것이 낫다 — **나무위키를 먼저 보고, 없는 것만 AI 로 채운다.**

§5 의 2~5번(AI 생성 경로)은 이미 만들어져 있고 **지우지 않는다.** 그대로 폴백이 된다.

### 9.1 접근 경로 — 실측 (2026-09-07)

평범한 UA(`CsiMusic/1.0`)로 확인했다. 토큰도 쿠키도 필요 없었다.

| 경로 | 결과 | 쓰임 |
|---|---|---|
| `/w/<제목>` | **200 / 404** | 존재 판정이 그대로 된다 |
| `/Search?q=` | **200, 결과 링크가 서버렌더** | **주 경로** |
| `/go/<제목>` | 301 | 정규 문서로 넘겨주기 |
| `/raw/` | 빈 SPA 껍데기 | 못 쓴다 |
| `/i/<토큰>` | 내부 검색 API | **쓰지 않는다** — 아래 |

`/i/…` 는 `x-chika`·`x-riko`·`x-you`·`x-namuwiki-nonce` 를 요구한다. 클라이언트 JS 가 만드는
**봇 차단 토큰**이라 재현하지 않는다. 공개 경로로 검색·판정이 다 되므로 그럴 이유도 없다.

가사는 **서버렌더로 HTML 에 들어 있다**(JS 실행 불필요).

### 9.2 문서 찾기 — 나무위키는 한국어 위주다

**문서 제목이 한국어다.** 일본어 원제는 인포박스에만 있는 경우가 많다.

| 곡 | 문서 제목 | `/w/<원제>` |
|---|---|---|
| 夜に駆ける | `夜に駆ける` | 맞음 |
| メイド☆至上主義 | `メイド☆至上主義` | 맞음 |
| **アクマバライ** | **`구마(음성 합성 엔진 오리지널 곡)`** | **404** |

그래서 `/w/<원제>` 직행은 **빠른 길일 뿐 주 경로가 아니다.** 전문검색은 일본어로 넣어도
본문에 원제가 있으면 찾아낸다(`アクマバライ` → 구마 문서가 결과에 나온다).

```
1) /w/<원제> 로 찔러 본다 — 200 이면 채택(싸다)
2) 404 면 /Search?q=<원제> → 후보 목록 → AI 가 고른다
```

후보 고르기를 AI 에 맡기는 이유: 검색 결과에는 곡 문서·앨범 문서·아티스트 문서·사용자
문서가 섞여 나온다. 다만 **AI 가 문서 제목을 지어내게 두지 않는다** — 검색이 돌려준 목록에서
고르게만 한다. 없는 문서를 고르면 404 로 즉시 걸린다.

### 9.3 구조는 문서마다 딴판이다 — 구조 파서를 만들지 않는다

문서 4개를 실제로 뜯어봤다.

| 문서 | 배치 | `lang='ja'` | 발음층 |
|---|---|---|---|
| 냐냐냐츄냐 | 줄마다 3행(원문/발음/번역) | 83개 | **있음** |
| メイド☆至上主義 | **3열 표**, 접기 틀 안 | **0개** | **있음** |
| 夜に駆ける | 770KB 대형 문서, 접기 틀 분산 | 3개 | **없음** |
| 지구과학 | **2열**(원문/번역) | — | **없음** |

같은 위키·같은 용도인데 마크업이 전부 다르다. `data-v-…` 는 Vue 스코프 해시라 배포마다
바뀌고, 클래스 이름도 스킨 개편 때 바뀐다. **구조 파서는 유지가 불가능하다.**

### 9.4 그래서 AI 를 쓴다 — 단, 생성이 아니라 **추출**

HTML 에서 태그를 걷어낸 텍스트를 AI 에 주고, **우리 가사 줄에 맞춰 발음·번역을 뽑아 오게**
한다. 배치가 3행이든 3열이든 2열이든 AI 가 읽어 낸다.

이건 §2 의 생성보다 **안전한 작업**이다:

- 정답이 입력 안에 있다. 지어낼 이유가 없다.
- **기계로 검증된다** — 뽑아 온 원문이 우리 가사 줄과 실제로 맞는지 대조할 수 있다.
  매칭률이 낮으면 통째로 버리고 폴백한다. 생성 경로에는 없던 안전장치다.
- §2.5b-4 의 검사(발음은 한글, 번역에 가나 없음, 빈 줄에 값 없음)를 그대로 재사용한다.
  단 **장음 기호 `ー` 는 예외로 허용**해야 한다 — 사람이 쓴 음차에 그대로 남아 있다.

곡이 큰 문서 안의 한 구획일 수 있으므로(§9.2 의 구마), 가사 구간만 잘라 보낸다.

### 9.5 폴백은 곡 단위가 아니라 **층 단위**

§9.3 표대로 **발음층이 있는 문서가 오히려 적다.** 번역만 있는 문서가 흔하다.
그러니 "나무위키에 있으면 통째로 쓴다"가 아니라, **얻은 층만 쓰고 빈 층은 AI 로 채운다.**

```
발음: 나무위키에 있으면 그것, 없으면 AI 생성
번역: 나무위키에 있으면 그것, 없으면 AI 생성
```

### 9.6 덤 — 가사 자체가 나무위키에만 있는 곡이 있다

보컬로이드·음성합성엔진 곡은 LRCLIB·Unison 에 없는 경우가 많은데 나무위키에는 있다.
**이건 이번 범위가 아니다**(가사 소스 사다리를 건드리는 별개 작업이다). 다만 여기서 만드는
가져오기·파싱이 그대로 재료가 되므로, 나중에 붙일 것을 염두에 두고 소스를 분리해 둔다.

### 9.7 출처 표기 — 필수

나무위키는 **CC BY-NC-SA 2.0 KR** 이다. 개인 LAN 서버라 NC 는 문제없지만 **출처 표기가
필요하다.** 앱에 Unison(ODbL) 표기 패턴이 이미 있으니(`np-credit`) 그대로 쓴다.

자동 수집은 나무위키 이용약관이 금지한다. 요청할 때만(§2.6) 곡 하나씩, 캐시를 붙여
최소로만 부른다.

### 9.8 실행 순서

1. **문서 찾기·본문 가져오기** — AI 가 안 붙은 부분. 단독으로 적중률을 잴 수 있다
2. AI 추출 + 원문 대조 검증 (§9.4)
3. `LyricsLayersService` 에 층 단위 폴백 끼우기 (§9.5)
4. 출처 표기 (§9.7)

1번의 적중률이 낮으면 나머지는 의미가 없다. **거기서 먼저 멈춰 재 본다.**

### 9.9 적중률 실측 (2026-09-07, 보관함 201곡 중 15곡 표본)

> **주의: 아래 "발음층 14%" 는 오측이다. §9.10 의 정정을 보라.**

§9.8 이 "1번의 적중률을 먼저 재라"고 한 결과다. 보관함에서 제목에 가나가 있는 곡 79개 중
15곡을 뽑았다(보컬로이드 원곡 · VTuber 커버 · 사용자 지목곡). 원문 대조는 앱이 이미 가진
가사(`/api/lyrics`)로 했다 — 우리 줄이 나무위키 문서 안에 실제로 있는지 세는 방식이다.

| 항목 | 결과 |
|---|---|
| 가사 있는 12곡 중 **문서 적중** | **7곡 (58%)** |
| 그중 **발음층이 있는 문서** | **1곡 (14%)** |
| 가사 없는 3곡에서 문서를 찾음 | 3곡 — §9.6 의 근거 |

**실패한 5곡의 원인은 대부분 검색어였다.** `恋愛裁判`·`群青` 은 문서가 있는데도 검색어가
커버 가수(`しぐれうい`)로 잡혀 못 찾았다. 제목에서 곡명을 뽑는 규칙이 조잡했던 탓이고,
**실제 구현에서는 앱이 이미 쓰는 `TitleParser`/`AiTitleParser` 의 결과를 그대로 넘기면 된다**
(그 파서는 같은 곡들의 가사를 LRCLIB 에서 이미 정확히 찾아 왔다). 즉 58% 는 하한이다.

`ヘイミスター`·`ゲンチアナ` 는 문서가 아예 없어 보인다 — 이건 못 고친다.

#### 반드시 짚어야 할 함정 두 개 (둘 다 실측에서 나왔다)

1. **후리가나를 걷어내지 않으면 원문 대조가 깨진다.** `<ruby>神<rt>かみ</rt></ruby>っぽいな`
   에서 태그만 지우면 `神かみっぽいな` 가 되어 한자가 든 줄이 전부 어긋난다. 이것 하나로
   적중률이 **25% → 58%** 로 뛰었다. `<rt>`·`<rp>` 는 본문에서 제거한다.
2. **일본어 원제는 한국어 문서로 넘겨주기된다.** `/w/神っぽいな` → `/w/신 같네`.
   리다이렉트를 따라가야 한다(`HttpClient` 기본값은 따라간다, `curl` 은 `-L` 필요).

#### 이 숫자가 설계에 주는 결론

**발음층은 드물다(14%).** 나무위키를 "발음의 주 소스"로 볼 수 없다. 대신 얻은 것이 있다.

| 층 | 나무위키 | 결론 |
|---|---|---|
| 가사 자체 | 다른 DB 에 없는 곡도 있다 | **가장 큰 수확** (§9.6) |
| 번역 | 흔하다 | 1순위로 쓸 만하다 |
| **발음** | **드물다(14%)** | **AI 생성이 주력이다** |

§9.5 의 층 단위 폴백은 그대로 옳다. 다만 기대치를 바꾼다 — **번역은 나무위키가 주고,
발음은 AI 가 만든다**고 보는 편이 실제에 가깝다. §5 의 2~5번(AI 생성)을 남겨 둔 것이
결과적으로 정답이었다.

### 9.10 §9.9 정정 — 발음층은 드물지 않다 (2026-09-07)

**§9.9 의 "발음층 14%" 는 틀렸다.** 판정에 쓴 정규식이 고장나 있었고, 문서를 직접 열어
세어 보니 정반대였다.

| 문서 | 원문 줄 | 원문 뒤 한글 2줄(=발음+번역) | 발음층 |
|---|---|---|---|
| セカイ | 62 | **51** | 있음 |
| 神っぽいな | 112 | **97** | 있음 |
| チューリングラブ | 122 | **113** | 있음 |
| ロキ | 62 | **59** | 있음 |
| 強風オールバック | 31 | **28** | 있음 |
| 可愛くてごめん | 62 | **62** | 있음 |
| メイド☆至上主義 | 88 | 5 | 있음(3열 표라 형태가 다름) |
| 선배는 남자아이(애니메이션) | 58 | 14 | 일부만 |

즉 **확인한 문서 8개 중 7개에 발음층이 있다.** 형태는 두 가지다 — 줄마다 3행(대다수)과
3열 표(§9.3). 후자는 "원문 뒤 한글 2줄" 패턴으로는 안 잡히므로 **판정을 형태에 의존하면 안 된다.**
어차피 뽑아내는 일은 AI 가 하므로(§9.4) 사전 판정은 필요 없다 — 문서를 찾았으면 그냥 보내고,
결과가 비면 그때 폴백한다.

#### §9.9 의 결론을 뒤집는다

| 층 | 나무위키 | 정정된 결론 |
|---|---|---|
| 가사 자체 | 다른 DB 에 없는 곡도 있다 | 큰 수확(§9.6) — 변동 없음 |
| 번역 | 흔하다 | 1순위 — 변동 없음 |
| **발음** | **흔하다(8중 7)** | **나무위키가 1순위. AI 는 폴백.** |

§9.5 의 층 단위 폴백은 그대로 옳고, 기대치는 원래 §9 의 것으로 되돌린다 —
**나무위키가 먼저, AI 가 폴백.** §9.9 의 "발음은 AI 가 주력" 문장은 폐기한다.

> 교훈: 있는지 없는지를 <b>형태로 짐작하지 말고</b> 실제로 열어서 세라. 판정기 버그 하나로
> 설계 결론이 통째로 뒤집혔다.

#### 사람이 눈으로 확인함 (2026-09-07)

문서 8개를 직접 열어 확인했다. **7개에 발음층이 있고**, `선배는 남자아이(애니메이션)` 만
일본어 원문뿐이다(§9.9 에서 `我がまま` 가 92% 로 잡힌 문서 — 가사 소스로는 쓸 수 있지만
발음·번역은 없다).

확인 과정에서 **AI 추출 프롬프트가 알아야 할 함정 두 개**가 더 나왔다.

| 함정 | 실제 예 | 대응 |
|---|---|---|
| **파트 분배 색상표** | `チューリングラブ`(나나오아카리/Sou/함께), `ロキ`(카가미네 린/미키토P/합창) | 가수 이름이 가사 줄처럼 섞여 들어온다. 무시하라고 프롬프트에 못 박는다 |
| **한 문서에 여러 버전** | `チューリングラブ` 는 `3.1 TV Ver.` 가 본편과 별도 | 짧은 버전에 걸리면 일치율이 떨어진다(`ロキ` 41% 의 원인으로 보인다) |

레이아웃은 지금까지 **두 가지**가 확인됐다 — 줄마다 3행(대다수)과 3열 표(`メイド☆至上主義`).
3열 표는 한 칸 안에 여러 줄이 `<br>` 로 들어가고 빈 줄로 절을 나눈다.
**둘 다 사람이 만든 형식이라 앞으로도 더 나올 수 있다.** 구조 파서를 안 만든 이유가 이것이다.

| 恋愛裁判 | 恋愛裁判 | 76% |
| 強風オールバック | 強風オールバック | 100% |
| 神っぽいな | 神っぽいな | 84% |
| チューリングラブ | チューリングラブ | 92% |
| セカイ | セカイ | 100% |

**6/6.** §9.9 에서 0% 로 놓쳤던 `群青`·`恋愛裁判` 이 둘 다 잡혔다 — 그때의 25%·58% 는
접근 방식의 한계가 아니라 검색어를 잘못 뽑은 결과였다.

검색어 규칙(§9.9 의 교훈을 코드로 옮긴 것):

1. 유튜브 구조화 메타의 곡명이 있으면 그것이 1순위다.
2. 대괄호 안(`[メイド☆至上主義]`)과 구분자로 자른 조각을 후보로 삼되, **커버 꼬리표를 뗀다**
   (`covered by`·`cover`·`feat.`·`歌ってみた`·`オリジナル楽曲`…).
3. **제목에서 앞에 있던 것부터 검색한다** — 곡명은 대개 맨 앞이고 커버 가수는 뒤에 온다.
   첫 시도에서 맞으면 남의 서버를 덜 두드린다(§9.7).

### 9.12 붙인 구조

```
LyricsLayersService.BuildAsync
  ├ JapaneseText.IsJapanese        일본어가 아니면 여기서 끝(§2.4)
  ├ NamuLyricsSource.FindAsync     후보 문서를 열어 우리 줄과 대조해 고른다(§9.2·§9.4)
  └ 층마다 · 덩어리마다
      ├ AiLyricsLayers.ExtractAsync   나무위키에서 베껴 온다(§9.4)
      └ AiLyricsLayers.BuildAsync     남은 줄만 만든다(§9.5)
```

- 나무위키가 그 덩어리를 **전부 덮으면 생성 호출이 아예 나가지 않는다.**
- 문서를 못 찾았거나 추출이 검증에 걸리면 **지금까지와 똑같이 생성만으로 돈다** —
  나무위키는 얹는 것이지 대체하는 것이 아니다.
- 캐시 키에 문서 제목이 들어간다 — 나중에 더 맞는 문서로 바뀌면 옛 결과가 따라오지 않는다.

**검증은 완화하지 않았다.** 발음은 여전히 한글만 허용한다(로마자·가나·한자 금지). 사람이 쓴
음차에 영어가 섞인 청크(`LOVE오 츄우뉴우`, `Boys be ambitious…`)는 통째로 버려지고 AI 가
한글로 다시 만든다 — 따라 부르는 줄이라 한글로 통일되는 편이 낫다.

추출에만 둔 예외는 두 가지이고, 둘 다 기준을 낮추는 것이 아니라 형태를 인정하는 것이다.

- **못 찾은 줄은 비워 둔다** — §9.5 층 단위 폴백의 전제다. 이걸 실패로 치면 부분 커버가 전부 버려진다.
- **장음 기호 `ー` 허용** — `세ー노` 처럼 사람이 쓴 음차에 그대로 남아 있다.

### 9.13 출처 표기 — 붙였다 (2026-09-07)

나무위키는 **CC BY-NC-SA 2.0 KR** 이라 화면에 띄울 때 출처를 밝혀야 한다. 붙인 방식:

| 자리 | 무엇 |
|---|---|
| `lyrics.layers_source` (신규 컬럼) | 베껴 온 나무위키 문서 제목. 전부 AI 가 만들었으면 NULL |
| 덩어리 캐시 | 값과 함께 `FromNamu` 를 저장한다 — 값만 캐시하면 다음 빌드에서 출처를 잃는다 |
| `/api/lyrics/{vid}` · `POST …/layers` | `layersSource` 로 내려준다 |
| 가사 패널 | `발음·번역 출처: 나무위키 「문서」 · CC BY-NC-SA 2.0 KR` (둘 다 링크) |

**한 줄이라도 실제로 베껴 왔을 때만 표기한다.** 문서를 찾았어도 추출이 검증에 걸려 AI 가
전부 만들었으면 `layers_source` 는 NULL 이다 — 기여하지 않은 곳을 출처로 다는 것도 잘못이다.

기존 Unison(ODbL) 표기와 같은 `.np-credit` 자리를 쓴다. 두 줄이 함께 뜰 수 있다(가사는
Unison, 발음·번역은 나무위키).

### 9.14 가사 자체를 나무위키에서 (2026-09-07) — §9.6 구현

보컬로이드·합성엔진 곡은 LRCLIB·Unison 에 없는데 나무위키에는 실려 있는 경우가 흔하다.
실제로 배포 로그에서 `アクマバライ`·`지구과학` 이 전부 `source=none` 이었다.

**소스 사다리의 맨 끝에 붙인다.** 여기까지 왔다는 건 다른 소스가 전부 빈손이라는 뜻이라,
붙여서 잃을 것이 없다(있던 가사를 밀어내지 않는다).

```
Unison(synced) → LRCLIB(synced) → Unison(plain) → LRCLIB(plain) → 인터넷 → 나무위키
```

#### 결정적 차이 — 대조할 원문이 없다

§9.2 의 `FindAsync` 는 후보 문서를 열어 **우리 가사 줄과 대조해** 맞는 문서를 골랐다. 그런데
가사가 없는 곡에는 대조할 것이 없다. 그래서 판정 방법이 완전히 달라진다.

| | 층 붙이기(§9.2) | 가사 가져오기(§9.6) |
|---|---|---|
| 문서 고르기 | 원문 일치율 | **가나 밀도**(가장 많이 실린 후보) |
| 맞는지 판정 | 원문 대조(기계적) | **AI 검증(작업 B)** |
| 틀렸을 때 | 층이 안 붙음 | **엉뚱한 가사가 뜸 ← 더 위험** |

그래서 **검증 없이는 절대 채택하지 않는다.** 다른 소스는 자체 메타(곡명·아티스트·길이)로
1차 거름이 되지만 나무위키는 그런 게 없어, `AiLyricsVerifier` 가 유일한 관문이다.

**`verdict` 가 null(판정 없음)이면 거부한다.** 다른 소스는 판정 없음을 통과로 보지만
(§2 의 비대칭 원칙 — 애매하면 살린다), 여기서는 반대로 간다. 검증되지 않은 스크랩을
가사로 띄우느니 없는 편이 낫다. AI 가 꺼져 있거나 검증 예산이 떨어지면 이 소스는 동작하지 않는다.

#### 비일본곡에 헛돈을 안 쓴다

`Queries()` 가 제목에서 가나 1자 또는 한자 2자 이상인 조각만 검색어로 삼는다. 한국어·영어
제목은 후보가 아예 안 나와 **네트워크 요청 없이** 즉시 끝난다.

#### 한계

- **싱크가 없다.** 나무위키 가사는 평문이라 `plain` 으로만 저장된다. 타임코드가 필요하면
  기존 자체 정렬(SelfSync)을 따로 돌려야 한다.
- 실패하면 `source=none` 이 7일 부정캐시된다(`NegativeTtl`) — 매번 다시 긁지 않는다.
- 토글은 `NAMU_LAYERS_ENABLED` + `AI_LYRICS_ENABLED` 를 함께 본다. 나무위키 기능 전체를
  한 스위치로 끄기 위해서다.

#### 출처 표기

가사를 나무위키에서 가져왔으면 가사 패널에 `가사 출처: 나무위키 · CC BY-NC-SA 2.0 KR` 이
붙는다(§9.13 의 층 표기와 별개 줄). 관리자 화면의 소스 라벨에도 `나무위키` 를 추가했다.

### 9.15 §9.2 정정 — 조각마다 일본어를 요구하면 안 된다 (2026-09-07)

§9.2 의 검색어 규칙("일본어가 없는 조각은 곡 문서로 이어지기 어렵다")이 **틀렸다.**
운영 로그에서 잡혔다.

```
곡: Earth Sci. (지구과학) / 初音ミク
나무위키 가사 후보: 桜日和とタイムマシン with 初音ミク (가나 437)
AI 가사 거부 — '桜日和とタイムマシン'의 가사입니다 (conf=0.99)
```

`Earth Sci.` 도 `지구과학` 도 일본어가 아니라 조각 단계에서 버려졌고, **남은 검색어가
`初音ミク`(보컬 이름)뿐**이라 미쿠가 참여한 아무 곡이나 물어 왔다.

나무위키는 한국어 위주라(§9.2) **곡 문서 제목이 한국어이거나 영문인 경우가 흔하다** —
정답 문서가 바로 `지구과학(VOCALOID 오리지널 곡)` 이었다.

고친 규칙:

- 일본어 여부는 **제목 전체로 한 번만** 본다. 전혀 없으면 요청을 내지 않는다(비용 방지).
- 조각은 한국어·영문이어도 그대로 검색어로 쓴다.
- **가수·보컬 이름과 같은 조각은 뺀다.** 곡이 아니라 그 사람이 참여한 문서가 전부 걸린다.
  (`music_artist` 를 넘겨 비교한다 — 두 호출부 모두 아티스트를 함께 전달하도록 고쳤다.)

고친 뒤 같은 곡의 검색어: `Earth Sci` · `지구과학` — 두 번째가 정답 문서 제목이다.

> 이번 건은 **AI 검증(§9.14)이 없었으면 엉뚱한 가사가 그대로 붙었을** 경우다. 대조할 원문이
> 없는 소스에 검증을 필수로 건 판단이 실제로 값을 했다.
